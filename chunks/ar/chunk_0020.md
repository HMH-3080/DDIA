لا يضمن مثال SQL أي ترتيب معيّن، ولذلك لا يمانع إن تغيّر الترتيب. لكن إذا كُتب الاستعلام بوصفه كودًا أمرًّا (imperative)، فلن تستطيع قاعدة البيانات أن تتأكّد أبدًا مما إذا كان الكود يعتمد على هذا الترتيب أم لا. وكون SQL أكثر تقييدًا في وظائفه يمنح قاعدة البيانات مساحة أكبر بكثير لإجراء التحسينات التلقائية (automatic optimizations).

وأخيرًا، فإن اللغات التصريحية (declarative) كثيرًا ما تناسب التنفيذ المتوازي. اليوم، أصبحت CPUs أسرع من خلال إضافة المزيد من الأنوية (cores)، لا من خلال التشغيل عند سرعات ساعة أعلى بكثير من قبل [31]. إن الكود الأمرّي صعب جدًا على التوازي عبر أنوية متعددة وآلات متعددة، لأنه يحدّد تعليمات يجب تنفيذها بترتيب معيّن. أما اللغات التصريحية فلها فرصة أفضل في أن تصبح أسرع من خلال التنفيذ المتوازي، لأنها تحدّد نمط النتائج فقط، لا الخوارزمية المستخدمة لتحديد النتائج. وقاعدة البيانات حرّة في استخدام تنفيذ متوازي للغة الاستعلام، إن كان ذلك مناسبًا [32].

## الاستعلامات التصريحية على الويب

مزايا لغات الاستعلام التصريحية لا تقتصر على قواعد البيانات فحسب. ولتوضيح هذه النقطة، لنقارن بين الأسلوب التصريحي والأسلوب الأمرّي في بيئة مختلفة تمامًا: متصفح الويب.

لنفترض أن لديك موقع ويب عن الحيوانات في المحيط. المستخدم يشاهد حاليًا صفحة أسماك القرش، لذا تضع عنصر التنقل «Sharks» كعنصر محدَّد حاليًا، على هذا النحو:

<ul> <li class="selected"> <p>Sharks</p> <ul> <li>Great White Shark</li> <li>Tiger Shark</li> <li>Hammerhead Shark</li> </ul> </li> <li> <p>Whales</p> <ul> <li>Blue Whale</li> <li>Humpback Whale</li> <li>Fin Whale</li> </ul> </li> </ul>

العنصر المحدَّد مُعلَّم بـ CSS class باسم "selected".

<p>Sharks</p> هو عنوان الصفحة المحدَّدة حاليًا.

الآن لنفترض أنك تريد أن يكون لعنوان الصفحة المحدَّدة حاليًا خلفية زرقاء، بحيث يُبرز بصريًا. وهذا سهل باستخدام CSS:

li.selected > p { background-color: blue; }

هنا يحدّد CSS selector li.selected > p نمط العناصر التي نريد تطبيق النمط الأزرق عليها، أي جميع عناصر <p> التي يكون والدها المباشر عنصر <li> ذا CSS class اسمه selected. أما العنصر <p>Sharks</p> في المثال فيطابق هذا النمط، في حين لا يطابق <p>Whales</p> ذلك لأن عنصر <li> الأب له يفتقر إلى class="selected".

<!-- page 67 -->

لو كنت تستخدم XSL بدلًا من CSS، لأمكنك فعل شيء مشابه:

<xsl:template match="li[@class='selected']/p"> <fo:block background-color="blue"> <xsl:apply-templates/> </fo:block> </xsl:template>

هنا، تعبير XPath li[@class='selected']/p يكافئ CSS selector li.selected > p في المثال السابق. وما تشترك فيه CSS وXSL هو أن كليهما لغتان تصريحيتان لتحديد تنسيق مستند.

تخيّل كيف ستكون الحياة لو كان عليك استخدام أسلوب أمرّي. في JavaScript، وباستخدام Document Object Model (DOM) API الأساسية، قد يبدو الناتج شيئًا كالتالي:

var liElements = document.getElementsByTagName("li"); for (var i = 0; i < liElements.length; i++) { if (liElements[i].className === "selected") { var children = liElements[i].childNodes; for (var j = 0; j < children.length; j++) { var child = children[j]; if (child.nodeType === Node.ELEMENT_NODE && child.tagName === "P") { child.setAttribute("style", "background-color: blue"); } } } }

يضبط هذا JavaScript العنصر <p>Sharks</p> بشكل أمرّي ليكون له خلفية زرقاء، لكن الكود فظيع. فهو ليس أطول بكثير وأصعب في الفهم من نظيرَي CSS وXSL فحسب، بل إنه يعاني أيضًا من بعض المشكلات الجسيمة:

• إذا أُزيلت class المحدَّد (مثلًا لأن المستخدم نقر على صفحة أخرى)، فلن يُزال اللون الأزرق، حتى لو أُعيد تشغيل الكود—وعليه سيبقى العنصر مُبرَزًا حتى تُحمَّل الصفحة بأكملها من جديد. أما مع CSS، فيكتشف المتصفح تلقائيًا متى لم تعد قاعدة li.selected > p سارية، ويزيل الخلفية الزرقاء بمجرد إزالة class المحدَّد.
• إذا أردت الاستفادة من API جديدة، مثل document.getElementsByClassName("selected") أو حتى document.evaluate()—والتي قد تحسّن الأداء—فيجب عليك إعادة كتابة الكود. وفي المقابل، يستطيع مصنّعو المتصفحات تحسين أداء CSS وXPath دون كسر التوافق.

vi. استخدم كلٌّ من IMS وCODASYL واجهات استعلام أمرّية. وكانت التطبيقات تستخدم عادةً كود COBOL للتكرار على سجلات قاعدة البيانات، سجلًا واحدًا في كل مرة [2, 16].

في متصفح الويب، فإن استخدام تنسيق CSS التصريحي أفضل بكثير من معالجة الأنماط بشكل أمرّي في JavaScript. وعلى نحو مماثل، في قواعد البيانات، تبيّن أن لغات الاستعلام التصريحية مثل SQL أفضل بكثير من واجهات الاستعلام الأمرّية.vi

## الاستعلام باستخدام MapReduce

MapReduce هو نموذج برمجة لمعالجة كميات كبيرة من البيانات على نحو جماعي عبر آلات متعددة، وقد شاعَه Google [33]. وتدعم بعض مخازن بيانات NoSQL، ومنها MongoDB وCouchDB، صيغة محدودة من MapReduce كآلية لتنفيذ استعلامات للقراءة فقط عبر مستندات عديدة.

يُشرح MapReduce بتفصيل أكبر في الفصل 10. وحتى الآن، سنناقش بإيجاز استخدام MongoDB لهذا النموذج.

MapReduce ليس لغة استعلام تصريحية ولا واجهة استعلام أمرّية بالكامل، بل يقع في مكان بينهما: إذ تُعبَّر منطق الاستعلام بشيفرات قصيرة (snippets)، يستدعيها إطار المعالجة مرارًا. وهو مبني على دالتي map (المعروفة أيضًا باسم collect) وreduce (المعروفة أيضًا باسم fold أو inject) الموجودتين في كثير من لغات البرمجة الوظيفية.

ولإعطاء مثال، تخيّل أنك عالم أحياء بحرية، وتضيف سجل ملاحظة (observation record) إلى قاعدة بياناتك كلما رأيت حيوانات في المحيط. والآن تريد توليد تقرير يوضّح كم عدد أسماك القرش التي رصدتها في كل شهر.

في PostgreSQL، يمكنك التعبير عن ذلك الاستعلام على هذا النحو:

SELECT date_trunc('month', observation_timestamp) AS observation_month, sum(num_animals) AS total_animals FROM observations WHERE family = 'Sharks' GROUP BY observation_month;

تحدّد الدالة date_trunc('month', timestamp) الشهر التقويمي الذي يقع فيه timestamp وتُعيد timestamp آخر يمثّل بداية ذلك الشهر. وبعبارة أخرى، فهي تُقرِّب timestamp إلى أقرب شهر.

يُفلتر هذا الاستعلام أولًا الملاحظات ليعرض فقط الأنواع في فصيلة Sharks، ثم يجمع الملاحظات حسب الشهر التقويمي الذي وقعت فيه، وأخيرًا يجمع العدد الإجمالي للحيوانات التي شوهدت في جميع ملاحظات ذلك الشهر.

ويمكن التعبير عن الشيء نفسه بميزة MapReduce في MongoDB على النحو التالي:

db.observations.mapReduce( function map() { var year = this.observationTimestamp.getFullYear(); var month = this.observationTimestamp.getMonth() + 1; emit(year + "-" + month, this.numAnimals); }, function reduce(key, values) { return Array.sum(values); }, { ); } query: { family: "Sharks" }, out: "monthlySharkReport"
